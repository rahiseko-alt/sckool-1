# 徹底監査の報告（2026-09-04）

動いている実環境（API・生徒の画面・管理画面・データベース）に対して、
配線・未検証箇所・見落とし・人の操作・異常操作・脆弱性を実際に叩いて確かめた記録です。
**コードを読んで「正しそう」ではなく、実際に操作した結果だけ**を証拠にしています。

## この監査のやり方と、正直な限界

- 20系統に分けた自動監査を回したが、**この開発環境のコンテナが数時間ごとに再起動**するため、
  6時間走った1周目（11系統・98件の指摘）は**記録が消え、個別に再検証できなかった**。
  自動監査は2度中断し、3度目は検証基盤の不具合で全滅した
- そこで**最も stakes の高い領域を、私が直接この環境で叩き直した**。以下の指摘と「堅牢だった項目」は
  すべて**このセッションで再現したコマンドと出力**が根拠。**未確認の領域は最後に明示する**
- 実データ規模: 企業約1,900社・出品約1,570件・台帳1,000万行超（過去のセッションが積んだもの）

## ユーザーの6つの問いへの結論

| 問い                                             | 結論                                                                                                                                                                             |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. 配線は全てつながっているか                    | **主要な操作は API→DB→画面まで一貫してつながっている**（買う・売る・経営・ログイン・権限を実測で確認）。ただし1周目の配線監査（画面の全ボタン網羅）は記録が消え未再検証 `[曖昧]` |
| 2. コードや緑/赤しか見ていない箇所は正しく動くか | **お金の計算・同時実行・権限は実物で堅牢**（下記「堅牢だった項目」）。テストの中身の多言語化だけ穴                                                                               |
| 3. 致命的な見落としはないか                      | **1件ある。** 秘密鍵を設定せずに公開すると、誰でも他社になりすませる（下記 C-1）                                                                                                 |
| 4. 人として操作して目的の動作は完了するか        | **日本語・英語では完走できる。** ただし**テストの中身が1言語のみ**で、他言語の生徒はテストを解けない（下記 H-1）                                                                 |
| 5. イレギュラーな操作で壊れるか                  | **壊れない。** 異常な入力・壊れた要求・同時操作を多数試したが、すべて丁寧に断られ、残高も在庫も狂わなかった                                                                      |
| 6. 脆弱性はないか                                | **設定さえ正しくすれば重大な穴は無い。** 唯一の重大は C-1（秘密鍵の初期値）。他は軽微〜中程度が4件                                                                               |

**一言でいうと**: 中身の作りは堅い。**公開前に「秘密鍵を必ず設定する」ことだけは絶対**で、
それを怠ると全部筒抜けになる。加えて、他言語でテストを使うなら題材の翻訳が要る。

## 公開（授業で使う）前に必ず直すもの

### C-1 [critical] 秘密鍵を設定し忘れると、誰でも任意の企業になりすませる

**何が起きるか**: 合鍵（ログイン時に配られる電子的な鍵）の正しさを確かめる「秘密鍵」が
設定されていないと、**プログラムに元から書いてある既定値**が使われる。既定値は誰でも知れるので、
攻撃者はその既定値で自分の手元で偽の合鍵を作り、**任意の Market ID の企業として**
買い物・出品・残高の閲覧ができてしまう。

**実際に確かめたこと**（いまの開発サーバーに対して）:

```
本物の合鍵の中身: {"actor_type":"customer","app_metadata":{"market_id":"MKT-HL74-VJ7U",...}}
偽造(secret=dev-only-not-a-secret) → /store/dashboard status=200 name=VICTIM ...   ← 通ってしまう
偽造(secret=supersecret)           → /store/dashboard status=401 login_required
alg=none                           → 401 login_required     ← 正しく拒否
誤った秘密鍵                        → 401 login_required     ← 正しく拒否
```

偽の合鍵で被害者企業のダッシュボードが 200 で開けた。**署名の偽造や alg=none は正しく弾く**ので、
守り自体は正しい。問題は**秘密鍵の初期値**にある。

**なぜ起きるか**: `apps/api/medusa-config.ts` が、環境変数 `JWT_SECRET` が無いと
文字列 `"supersecret"`（Medusa の有名な既定値）に、`COOKIE_SECRET` も同様にフォールバックする。
`scripts/run-api.mjs` は開発用に `dev-only-not-a-secret` を既定で入れている。
**どちらも「誰でも知れる固定値」**なので、本番で `JWT_SECRET` を設定し忘れると即座に破られる。

**どう直すか**（順に強い）:

1. **`medusa-config.ts` を、秘密鍵が未設定または既定値のときは起動を止める**作りにする
   （黙ってフォールバックしない）。これが根本的な対策
2. 最低でも `docs/deploy.md` の「必ず変える」を、手順の**最初の必須項目**に格上げする
   （現状は「まだ決めていないこと」に書かれていて弱い）

**現状の緩和**: `docs/deploy.md` に「開発用の既定値を使わない」とは書いてある。
だが**書き忘れても起動してしまい、破られるまで誰も気づかない**のが危険。

## 授業で他言語を使うなら直すもの

### H-1 [high] テストの中身（題名・題目・設問）が1言語のみで、他言語の生徒は解けない

**何が起きるか**: 生徒の画面の**枠**（ボタン・「5問」「ボーナス1,500MP」等）は6言語に翻訳される。
しかし**テストそのものの中身**——題名・題目・設問・選択肢——は作成時の1言語で固定される。

**実際に確かめたこと**（ネパール語とタイ語で生徒の画面を最後まで操作）:

```
[ne-NP] テスト画面: ... Knowledge Challenge  विषय: 独占禁止法 ...
[th-TH] テスト画面: ... Knowledge Challenge  หัวข้อ: 独占禁止法 ...
```

枠はネパール語・タイ語になっているのに、**題名が英語（Knowledge Challenge）、題目が日本語（独占禁止法）**
のまま。ネパール語しか読めない生徒は、テストに何が書いてあるか分からない。

**なぜ問題か**: テストはボーナス MP の入口（受け入れ基準 E 系）で、生徒の journey の一部
（受け入れ基準 I4「1言語で完走」）。**他言語の生徒はこの経路を実質使えない。**

**どう直すか**: 商品名・説明と同じ「原文＋各言語の翻訳」の仕組みをテストにも広げる。
または、授業で使う言語ごとにテストを別々に用意できるようにする。
**MVP から外すと決めるなら、その旨を `docs/requirements.md` に明記する**
（現状は「テスト」が翻訳対象に挙がっているので、いまは穴）。

## あとで直せばよいもの（軽微〜中程度）

### M-1 [medium] 再発行コードの試行に回数制限が無い

ログインは5回失敗で15分ロックされる（実測で確認）。しかし**パスワードの再発行
（`/store/recovery`）は別の経路で、ロックの対象外**。誤ったコードを何度でも試せる。

```
再発行コード誤り6連続: 401,401,401,401,401,401   ← ずっと試せる
ログイン失敗7連続:     401,401,401,401,401,429,429 ← こちらは5回でロック
```

**実害は小さい**: 再発行コードは `XXXX-XXXX-XXXX`（紛らわしい文字を除いた英数字）で組み合わせが
膨大なため、総当たりは現実的でない `[曖昧: コードの桁数と文字種から実行不能と判断したが、
攻撃コストは精密には計算していない]`。ただし守りの層としてログインと揃えるのが望ましい。

**どう直すか**: 再発行の失敗も Market ID ごとに数えてロックする。

### M-2 [medium] 合鍵の中に「再発行コードのハッシュ」が入っている

合鍵（JWT）は誰でも中身を読める形式で、その中に `recovery_code_hash`（パスワード再発行用の
合言葉のハッシュ）が含まれている。

```
本物の合鍵の中身: {..."app_metadata":{..."recovery_code_hash":"c05d6241...:5eea63a9..."}}
```

ハッシュ化されており元のコードは復元できない設計だが、**再発行の資格情報のハッシュを
持ち歩く合鍵に載せる**のは避けるのが定石。合鍵が漏れたときの被害を1つ増やす。

**どう直すか**: 合鍵の中身に `recovery_code_hash` を入れない（必要なときにデータベースから引く）。

### L-1 [low] 画像URLが検証されない

出品の画像URLに `javascript:alert(1)` を入れても保存され、`<img src>` にそのまま入る。

```
javascript: が img src に入っている: true
（ただし dialog は出ない = 現代のブラウザは img の javascript: を実行しない）
```

**実行はされない**（無害）が、URL が検証されないため、任意の外部サーバーへ画像要求が飛ぶ
（プライバシー・追跡）、壊れた画像が出る、といった副作用がある。

**どう直すか**: 画像URLは `http(s)://` で始まる形だけ受け付ける。

## 堅牢だった項目（実物で確かめて問題が無かったもの）

「緑/赤しか見ていないのでは」という懸念に対し、**実際に壊そうとして壊れなかった**ものを列挙する。

### お金と同時実行（最重要・全て実測で健全）

| 確かめたこと                                        | 結果                                                                                                      |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| 購入で市場全体の MP 総量が保たれるか                | **保たれる**（前後の差 0）                                                                                |
| 作成時に残高・権限を注入できるか（mass assignment） | **できない**（`balance:9999999` を送っても初期資金は 100,000。`market_id:MKT-FAKE` も無視され機械が採番） |
| 在庫1個を10社が**同時に**買う                       | **1社だけ成功**、残り在庫 0                                                                               |
| 残高10万の企業が9万の商品5個を**同時に**買う        | **1個だけ成功**、残高 10,000（負にならない）                                                              |

同時実行の守り（企業ごとの順番待ち＋在庫の条件付き更新）は実際に効いている。

### 権限（越境を全て試して全て拒否）

| 試したこと                                 | 結果                 |
| ------------------------------------------ | -------------------- |
| 企業Aが企業Bの商品を消す・変える           | 404（拒否）          |
| 合鍵なしで購入                             | 401                  |
| 生徒の合鍵で `/admin/*` を8経路叩く        | **全て 401**         |
| 自分のダッシュボードが自分のものか         | 自分（合鍵から特定） |
| 合鍵の署名を偽造 / alg=none / 誤った秘密鍵 | **全て 401**         |

### 注入・露出

| 試したこと                                                  | 結果                                              |
| ----------------------------------------------------------- | ------------------------------------------------- |
| 並べ替え（sort）に SQL を注入                               | 無効（許可した値以外は revenue に戻す）           |
| 言語指定（locale）に SQL を注入                             | 無効（パラメータ化されている）                    |
| テストの正解が API 応答に含まれるか                         | **含まれない**（設問は id・prompt・choices のみ） |
| 別 origin（evil.example.com）から呼べるか                   | 許可ヘッダが返らない（拒否）                      |
| ランキング応答に相手の Market ID が漏れるか                 | 漏れない（要件38）                                |
| 存在するID/しないIDでログイン失敗の文言が違うか             | 同一（アカウント列挙不可）                        |
| 壊れたJSON・型不正を送って 500 やスタックトレースが漏れるか | 全て 400、内部情報の漏れなし                      |

### 画面（生徒の画面）

| 確かめたこと                                                           | 結果                                                                   |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 商品名・企業名・説明に `<script>`/`<img onerror>` を入れて実行されるか | **実行されない**（React が自動でエスケープ。生のタグは画面に入らない） |
| 幅375pxで横スクロールが出るか                                          | **全画面・全言語で 0**（ネパール語・タイ語含む）                       |
| ネパール語・タイ語で枠（ナビ・ボタン）が翻訳されるか                   | 翻訳される（残る日本語はテスト題目のみ＝H-1）                          |
| ログイン5回失敗でロックされるか                                        | 5回で 429、ロック中は正しいPWも 429                                    |

## 確かめられなかったこと

**書いていないことと「問題が無い」ことは違う。** 次はこのセッションで再検証できていない。

- **1周目の自動監査98件の個別再検証。** コンテナ再起動で記録が消えた。内訳は
  「重大2・重い22・中38・軽24・情報12」だったが、**どの項目かの本文は復元できていない** `[曖昧]`。
  ただし、その中で最も重い領域（権限・お金・注入・多言語・画面）は上記のとおり**私が直接叩き直した**
- **画面の全ボタン網羅**（配線の1周目）。買う・売る・経営・ログインの主要動線は実測したが、
  管理画面の5ページ全ボタンと、生徒の画面の隅々まではこのセッションで押し切っていない `[曖昧]`
- **定期実行（ボーナス失効）が時間をおいて本当に発火するか。** 過去のセッションの記録では
  「毎分設定で発火を確認」とあるが、このセッションでは待って再確認していない `[曖昧]`
- **台帳の書き換え不能（K3）をデータベースから破る試み。** 過去の `docs/release-check.md` で
  「引き金で拒む」ことを確認済みだが、このセッションでは再実行していない
- **60人同時アクセス時の画面の応答速度。** 台帳1,000万行での一覧・ランキングの実測はしていない `[曖昧]`
- **母語話者による翻訳の質**（4言語）。機械的な過不足は 0 だが、訳が自然かは人にしか判断できない
  （既知の積み残し。`docs/neglected-log.md` 参照）

## まとめ

**授業で使える水準の作りだが、公開前に C-1（秘密鍵）だけは絶対に手当てすること。**
それを怠ると全企業が筒抜けになる。他言語でテストを使うなら H-1（テストの翻訳）も要る。
残りの4件は、あとから直しても授業は成立する。

中身の堅牢さ——お金の保存則、同時実行、権限、注入耐性、375px対応——は
**実際に壊そうとして壊れなかった**。ここは信頼してよい。
