# 失敗行動台帳

**失敗したと気づいた、その場で書く。書くのはその行動を取った本人（AI自身）。**
書きっぱなしでよい。自由記述で構わないが、**日時は必須**。

## 何を書くか

**行動を書く。結果は書かない。** 結果（バグ・CI赤など）は `docs/test-policy.md` と
テスト・CIの担当領域であり、ここに書くと二重管理になる。ここに書くのは「何を試みたか」
「どんな判断・手順で進めたか」という、AI自身の行動。

例:

- ❌「typecheck.sh が worktree で動かないバグがあった」（結果）
- ✅「hook のロジック検証を、実際に worktree へ入らず手動 JSON パイプだけで済ませた」（行動）

最終的にうまくいったかどうかを待つ必要はない。「この行動で本当に十分か分からない」と
気づいた時点で、その場で書いてよい。

## なぜ存在するか

**正解を探すために読むのではない。失敗行動を繰り返さないために読む。**

正解が何かは分からなくても、「これは確実に失敗する行動だ」と分かっているものは減らせる。
台帳を読んでも次に何をすべきかは書いていない。しかし「これをやってはいけない」は増えていく。
選択肢が100あるとして、失敗行動だと分かっているものを50除外できれば、残り50から探す方が
正解に近づきやすい。これが唯一の価値。

## いつ読むか

通常のセッションでは読まない（コンテキストを圧迫するため）。読むのは次のときだけ:

- ユーザーが明示的に「読め」と指示したとき
- **行き詰まっていて、何が悪いか分からないとき。** ただし読む前に必ずユーザーへ
  「失敗行動台帳を読みますか？」と確認し、Yes と言われてから読む

読むときは自分で読まず `failure-reviewer` サブエージェントに委譲する。重複した記録の整理も
そこで行う。詳細は `AGENTS.md`「失敗と放置の記録」を参照。
