# 公開の手順

生徒が自分の端末から使えるようにするための手順です。**まだ一度も実行していません**
（この開発環境には Vercel の資格情報が無く、外へ出す操作ができません）。

## どれをどこに置くか

このプラットフォームは3つの部品でできています。**Vercel に置けるのは1つだけ**です。

| 部品                            | 中身                                   | 置き場所                           |
| ------------------------------- | -------------------------------------- | ---------------------------------- |
| 生徒の画面（`apps/storefront`） | 組み立て済みの HTML と JavaScript だけ | **Vercel でよい**                  |
| バックエンド（`apps/api`）      | 常に動き続けるサーバー                 | **Vercel では動かない**（下記）    |
| PostgreSQL と Redis             | データの保存場所                       | 貸してくれるサービスを別に契約する |

### なぜバックエンドは Vercel に置けないか

Vercel は「呼ばれたときだけ短く動く」形の置き場所です。このバックエンド（Medusa）は
**動き続けることを前提にした作り**で、次の3つが要ります。

- **止まらないサーバー本体**
- **裏で動く処理**（毎時0分にボーナスを失効させる仕組みが実際に動いています）
- **PostgreSQL と Redis への常時接続**

Medusa の公式文書も、バックエンドは「Node.js のサーバーを動かせる置き場所」が必要で、
Vercel の名前は**生徒の画面（フロントエンド）の例としてだけ**挙げています。

- https://docs.medusajs.com/learn/deployment

## 生徒の画面を Vercel に置く

リポジトリ直下の `vercel.json` に組み立て方を書いてあります。Vercel 側でこのリポジトリを
つないだあと、**環境変数を2つ**入れてください。片方でも欠けると、市場に商品が1つも
出ません（公開鍵が無いと Store API が全て 400 を返すため）。

| 変数名                 | 中身                                                     |
| ---------------------- | -------------------------------------------------------- |
| `VITE_BACKEND_URL`     | バックエンドの住所（例: `https://api.example.com`）      |
| `VITE_PUBLISHABLE_KEY` | `pnpm run seed` で作られる公開鍵（`pk_` で始まる67文字） |

**この2つは組み立てるときに埋め込まれます。** あとから変えたときは、Vercel で
組み立て直してください（環境変数を変えるだけでは反映されません）。

## バックエンド側で要る設定

生徒の画面の住所を、バックエンドが「話してよい相手」として知っている必要があります。
`STORE_CORS` と `AUTH_CORS` の**両方**に入れてください。片方だけだと
**「市場は開けるのにログインだけ失敗する」**状態になります（実際に起きました）。

キー名の一覧は `apps/api/.env.template` にあります。

## 無料の置き先を調べた結果

**バックエンド（止まらないサーバー）を無料で置ける先は、実質 Oracle Cloud の
「Always Free」だけ**でした。ほかは、この用途には使えません。

| 候補                         | 結果                                                                  |
| ---------------------------- | --------------------------------------------------------------------- |
| **Oracle Cloud Always Free** | **使える。** 2コア・12 GB・ディスク200 GB・通信10 TB/月。**期限なし** |
| Fly.io                       | 無料枠の記載が無く、組織にカード登録が必要                            |
| Koyeb                        | 常時動くサーバーの無料枠なし（PostgreSQL が月5時間だけ）              |
| Supabase                     | ユーザーの指示により対象外                                            |

### Oracle を選んだときに起きうること

**60人が一斉に操作しても足ります（実測）。** 60社・375件の購入を19.4秒（毎秒19件）で
処理したときの最大が **CPU 1.33コア / メモリ 1,290 MB**。枠は2コア・12 GB なので、
CPU は3分の2、メモリは10分の1しか使いません。実際の授業は毎秒19件も買わない
（60人が1分に1回でも毎秒1件）ので、19倍の余裕があります。
**測ったのは x86 で、ARM は1コアあたり遅い**[曖昧] が、この余裕を食い潰す差ではありません。

**いちばん大きい落とし穴は「使っていないと取り上げられる」こと。** Oracle は Always Free の
サーバーを、7日間つづけて次の3つが**同時に**成り立つと回収します。

> CPU utilization for the 95th percentile is less than 20% /
> Network utilization is less than 20% /
> Memory utilization is less than 20% (applies to A1 shapes only)

**このプラットフォームは3つとも当てはまります。** 上の実測のとおり、
60人が一斉に買っている瞬間ですらメモリは 12 GB の 20%（2.4 GB）に届きません。
授業が週1回なら、長期休暇で条件が揃います。

**回収が「停止」なのか「削除」なのか、事前に知らせが来るのか、データが残るのかは
公式文書に書かれていません**[曖昧]。

3つは **かつ** なので、1つ崩せば対象外になります。PostgreSQL に 3 GB 程度を常に
握らせておけば、メモリが 20% を超えて対象から外れます。

そのほか:

- **そもそも作れないことがある。** 本拠地リージョンで枠が無いと `out of host capacity`。
  本拠地リージョンは申し込み時に決まる（公式は「慎重に選べ」とだけ書き、変更できるかは
  書いていない）[曖昧]。別の可用性ドメインを試すか、時間をおいて再試行する
- **1台に全部載せるので、その1台を失うと授業のデータが消える。** Always Free に
  ボリュームのバックアップが5つ含まれるので、それを使う運用が要る
- **申し込みに本人確認のクレジットカードが要る**（課金はされない）

根拠:

- https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm
- https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier.htm
- https://fly.io/docs/about/pricing/
