# 第1部 要件（原文）

## 1. 目的

60人程度の生徒が、それぞれ仮想企業を経営し、**「どこで・誰に・何を・いくらで・どう知らせて・どう売るか」**というマーケティング活動を、実際の売買を伴う形で体験する。

単なる商品企画コンテストではなく、

- 市場調査
- 商品・サービス開発
- 価格設定
- 広告
- 販促
- 販売
- 購入
- 売上・利益管理
- 競争
- 法規制
- 改善

までを、一つの閉じた仮想市場内で循環させる。

最終目的は、**「売れる仕組みを作ることがマーケティングである」ことを体験によって理解させること。**

## 2. 基本構造

### 参加者

#### 生徒

60名程度。

原則として1人1社の仮想企業を持つ。

各企業は、

- 資本金
- 売上
- 経費
- 利益
- 在庫または提供可能数
- 商品・サービス
- 広告
- 顧客

を持つ。

#### 教員

4名程度。

原則として**販売者ではなく消費者として市場に参加する。**

生徒の商品・サービスを購入できるが、市場を恣意的に操作しないよう一定の購入ルールを設定する。

## 3. 仮想通貨

現実のお金は使用しない。

プラットフォーム内専用通貨を使用する。

仮称：

**Market Point / MP**

など。

### 初期資産

全企業に同額の初期資金を配布する。

例：

- 初期資本金：100,000MP

重要なのは金額そのものではなく、**全員が同条件でスタートすること。**

## 4. 生徒が資金を使う対象

「誰も買わない市場」を防ぐため、資金を保有しているだけでは有利にならない構造にする。

企業活動には費用が発生する。

例：

| 項目               | 支出 |
| ------------------ | ---- |
| 商品開発           | 必要 |
| 市場調査           | 必要 |
| 広告出稿           | 必要 |
| 販促キャンペーン   | 必要 |
| 出店・掲載         | 必要 |
| 商品改良           | 必要 |
| 外部データ購入     | 必要 |
| AI・制作ツール利用 | 必要 |
| 特別販売枠         | 必要 |

したがって、

> お金を使わない企業は成長できない

という構造にする。

## 5. 商品・サービス

生徒は自由に商品またはサービスを企画する。

ただし現実の商品を製造する必要はなく、仮想商品でもよい。

例：

- ロゴ制作
- SNS投稿制作
- 動画制作
- キャッチコピー
- AIプロンプト
- イベント企画
- 学習支援
- リサーチ
- デザイン
- コンサルティング
- 仮想飲食店
- 仮想アプリ
- 仮想旅行商品

重要なのは商品そのものより、

**誰のどんな課題を解決する商品なのか**

を明確にすることである。

## 6. 商品登録

最低限、以下を登録する。

### 必須項目

- 商品名
- 商品説明
- ターゲット顧客
- 解決する課題
- 販売価格
- 提供可能数
- 商品画像
- 販売期間

可能であれば、

- 原価
- 開発費
- 想定利益
- USP
- 購入後のメリット

も設定する。

## 7. 市場

全企業の商品が一覧表示される。

AmazonやECモールのような構造を想定する。

ユーザーは、

- 商品を見る
- 比較する
- 詳細を見る
- 購入する

ことができる。

## 8. 購入

生徒は他企業の商品を購入できる。

自己購入は禁止する。

購入すると、

購入者：

> 残高 − 商品価格

販売者：

> 残高 ＋ 商品価格

となる。

すべての取引履歴を保存する。

## 9. 生徒が購入する理由

ここが本システムの最重要要件。

単に「自由に買ってください」では市場が成立しない。

そのため、**購入に意味を持たせる。**

例えば企業活動に必要なものを他社から買う。

例：

自社の商品を売るために、

- デザイン会社からロゴを買う
- 広告会社から広告を買う
- リサーチ会社から市場調査を買う
- コピー会社からキャッチコピーを買う
- 動画会社からPR動画を買う

という構造にする。

つまり、

> 生徒自身が消費者であると同時に企業でもある。

## 10. 教員消費者

市場に外部需要を発生させるため、教員4名程度を「買うだけの参加者」とする。

ただし自由購入だけでは、

- 贔屓
- 人気者への集中
- 知り合いへの購入
- 特定企業への偏り

が発生する。

したがって購入にルールを設ける。

## 11. 教員購入ルール

教員には一定期間ごとに購入予算を与える。

例：

- 1週間：10,000MP
- 1授業：5,000MP

など。

ただし単純な自由購入ではなく、

### 購入課題方式

を基本とする。

例：

> 「新入生向けイベントを開催するための商品を購入してください」

教員は市場の商品から条件に合うものを選ぶ。

これにより、

**マーケティングによって購入される**

という状態を作る。

## 12. 広告

企業は広告費を支払って広告を掲載できる。

### 広告例

- トップページ広告
- 商品一覧上位表示
- バナー広告
- おすすめ枠
- タイムライン広告
- 特集枠

広告掲載には費用が必要。

## 13. 広告効果

広告には最低限、

- 表示回数
- クリック数
- CTR
- 購入数
- 広告費
- 売上

を記録する。

可能なら、

**ROAS**

も表示する。

## 14. 販促

企業は販促施策を実施できる。

例：

- 値引き
- クーポン
- セット販売
- 期間限定販売
- 数量限定
- 初回割引
- リピート割引

これによって価格戦略を体験する。

## 15. 市場調査

企業は市場データを閲覧できる。

ただし情報量によって課金してもよい。

無料：

- 売れ筋ランキング
- 商品数
- 平均価格

有料：

- ターゲット別需要
- 市場規模
- 検索数
- 競合分析
- 購買傾向

これにより、

**リサーチに投資する意味**

を作る。

## 16. 経営ダッシュボード

各企業にダッシュボードを用意する。

最低限表示するもの：

- 現在残高
- 売上
- 支出
- 利益
- 販売数
- 購入数
- 広告費
- 商品別売上

可能であれば、

- 利益率
- ROAS
- 顧客数
- リピート率

も表示する。

## 17. マーケティング学習との接続

各企業は以下を定義する。

1. どこで
2. 誰に
3. 何を
4. いくらで
5. どう知らせて
6. どう売るか

そして実際の売上結果を見る。

売れなければ、

どこに問題があるのかを分析する。

特に、

> 上流の変更は下流全体に影響する

という構造を授業で体験させる。

例：

「誰に」を変更した場合、

- 商品
- 価格
- 広告
- 販売方法

も再検討する。

## 18. 日本のビジネス法教育

この市場には、日本の実際の商取引ルールを簡略化して導入する。

特に重要なのは、

### 独占禁止法

授業用には、

- 私的独占
- 不当な取引制限
- 不公正な取引方法

を中心に扱う。

## 19. カルテル禁止

企業同士で、

> 「みんな1000MPで売ろう」

など価格を相談して決定する行為は禁止。

また、

> 「この市場にはA社だけ販売させよう」

といった市場分割も禁止。

発覚した場合には運営から警告・ペナルティを与える。

## 20. 仲良しグループ対策

生徒同士の市場なので、

> 仲が良いから買う

という問題は必ず発生する。

完全な禁止は現実的ではない。

したがってシステム上で異常取引を可視化する。

例：

A→Bへの購入が極端に多い
B→Aへの購入が極端に多い

場合、

**相互取引率**

を表示する。

教員管理画面では、

- 特定相手への購入集中
- 相互購入
- グループ内取引

を確認できる。

## 21. 循環取引対策

以下のような取引は禁止。

A → B
B → C
C → A

という形で、実質的に資金を回す行為。

これを授業上、

**架空・循環取引**

として扱う。

## 22. 贔屓対策

教員購入については購入ログを公開または教員間で共有する。

確認項目：

- 企業別購入額
- 購入回数
- 教員別購入先
- 購入集中率

これにより、

意図しない偏りを防ぐ。

## 23. 市場支配

優秀な企業が市場を独占すること自体は禁止しない。

むしろ教材にする。

例えば、

> 一社が市場シェア70%

になった場合、

なぜその会社が強いのかを分析する。

ただし、

- 排他的取引
- カルテル
- 妨害行為

などは別問題として扱う。

## 24. 倒産

資金が一定以下になった場合、

「経営危機」とする。

完全に0になった場合、

倒産としてもよい。

ただし授業なので再起不能にはしない。

例：

- 融資
- 追加出資
- 事業再生
- 商品ピボット

などの救済イベントを用意する。

これはむしろ重要な教材になる。

## 25. ランキング

ランキングは売上だけにしない。

売上だけにすると、

> 勝者総取りゲーム

になってしまう。

複数指標を用意する。

例：

- 売上
- 利益
- 利益率
- 顧客数
- ROAS
- 成長率
- 市場シェア
- 顧客評価

## 26. 教員管理画面

教員は市場全体を確認できる。

最低限：

- 全企業
- 残高
- 売上
- 利益
- 取引
- 商品
- 広告
- ランキング
- 資金移動

を閲覧する。

さらに、

### 不正・異常検知

- 相互購入
- 特定グループ内取引
- 異常価格
- カルテル疑い
- 循環取引

を確認できるようにする。

## 31. このシステムの本質

これはECサイトではない。

**「マーケティングを体験するための市場シミュレーター」**

である。

さらに、

単なる経営ゲームでもない。

中心に置くべき構造は、

> 顧客を決める
> ↓
> 商品を作る
> ↓
> 価格を決める
> ↓
> 知らせる
> ↓
> 売る
> ↓
> 結果を見る
> ↓
> 上流へ戻って改善する

というマーケティングシステムそのもの。

そして、その活動を**日本の市場ルール・商慣習・独占禁止法などの制約の中で行わせる**。

## 32. 学習テスト・ボーナス制度

授業内で任意の確認テストを実施できる。

テストはマーケティング、経営、日本の商習慣・法律など、授業内容の理解確認を目的とする。

高得点を取得した生徒には、**即時に仮想資金を付与する。**

例：

| 得点      | ボーナス |
| --------- | -------: |
| 60点未満  |      0MP |
| 60〜79点  |    500MP |
| 80〜89点  |  1,000MP |
| 90〜100点 |  1,500MP |

金額は授業設計時に変更可能とする。

### ボーナスの性質

通常資金とは別に、

**ボーナス残高**

として管理する。

ボーナスには短い有効期限を設定する。

例：

> 獲得から7日間、または次回授業終了まで

期限を過ぎた未使用分は消滅する。

### 支払い優先順位

企業が支払いを行う場合、

**①ボーナス残高 → ②通常残高**

の順番で自動的に消費する。

生徒自身がどちらを使うか選択する必要はない。

例：

通常残高：10,000MP
ボーナス：1,500MP
2,000MPの商品を購入

↓

ボーナス：0MP
通常残高：9,500MP

とする。

### テストだけでは経営できない設計

テストボーナスはあくまで、

**学習成果に対する一時的な経営支援**

と位置付ける。

したがって、

> テストを受け続ければ商品を売らなくても経営できる

状態にはしない。

具体的には、

**1回のテストボーナス ＜ 企業活動に必要な平均支出**

となるよう金額を設定する。

例えば1期間の標準的な企業活動に5,000〜10,000MP程度必要なら、テストによる獲得額は1,000〜1,500MP程度に留める。

さらに、

- 同じテストからボーナスを得られるのは1回のみ
- ボーナスには短い有効期限
- ボーナスから優先的に消費

の3つだけをルールとする。

## 33. この制度を入れる理由

これは単なるゲーム要素ではなく、

**「勉強すると経営上少し有利になる」**

という授業設計になる。

たとえば独占禁止法を勉強して高得点を取る。

↓

1,500MP獲得

↓

その資金を広告に使う

↓

売上が増えるか試す。

つまり、

**学習 → 資源獲得 → 経営判断 → 市場結果**

までが一続きになる。

これはこの授業との相性がかなり良いです。

ただし、ここから「連続ログインボーナス」「レベル」「経験値」「スキルツリー」などまで追加すると、経営シミュレーターではなくゲーム設計が中心になってしまいます。

したがって**追加するのは「期限付きボーナス残高」だけ**で十分です。既存の残高処理に「bonus_balance・expires_at・ボーナスから先に引く」を追加する程度なので、MVPにも入れて問題ないと考えます。

## 34. 多言語対応

初期リリースから以下の6言語に対応します。

| 言語             | locale  |
| ---------------- | ------- |
| 日本語           | `ja-JP` |
| 英語             | `en`    |
| 中国語（簡体字） | `zh-CN` |
| ベトナム語       | `vi-VN` |
| ネパール語       | `ne-NP` |
| タイ語           | `th-TH` |

画面右上などに言語切替を常設し、ログイン前でも変更可能にします。

Medusa自体には現在Translation Moduleがあり、商品名・商品説明・カテゴリ等をlocale別に管理できます。Store APIもlocale指定に対応しています。したがって、ここはOSS基盤と比較的きれいに接続できます。

ただしMercurのStorefront自体は、2026年8月時点でも言語・通貨・配送地域を独立して扱う改善Issueが残っています。したがって、**「Mercurを入れれば6言語対応完成」とは考えない方がいい**です。Storefront側のUI翻訳は我々で整備する前提にします。

### 翻訳対象

最低限すべて翻訳します。

- ナビゲーション
- ボタン
- エラーメッセージ
- 商品登録画面
- 購入画面
- 企業ダッシュボード
- MP残高
- 広告
- テスト
- ランキング
- 教員管理画面
- 法律・ルール説明
- チュートリアル

つまり、**日本語が分からなくても一人で操作できること**を合格条件にします。

商品説明など、生徒自身が入力する文章については少し分けます。

MVPでは、

> 入力した原文 + 任意の各言語翻訳

とします。

自動翻訳まで最初から入れるとAPIコスト・誤訳管理・UIが増えるので、MVPでは不要です。

## 35. 匿名認証

ここは通常のECとは設計を変えます。

**システム内に生徒の個人情報を保存しません。**

保存禁止：

- 氏名
- メールアドレス
- 電話番号
- 住所
- 生年月日
- 学籍番号
- SNSアカウント
- Googleアカウント
- Microsoftアカウント

したがって、
Googleログインなども採用しません。

### アカウント

システムがランダムなMarket IDを発行します。

例：

```text
Market ID
MKT-7F4K-29QX
```

生徒は、

```text
Market ID
+
パスワード
```

だけでログインします。

企業名も自由な仮想企業名です。

```text
Market ID：MKT-7F4K-29QX
企業：
NEKO DESIGN
残高：
96,500 MP
```

システムから見れば、

> 「MKT-7F4K-29QXという企業アカウント」

でしかありません。

誰が使っているかは知りません。

## 36. パスワードリセット

ここが匿名認証で一番問題になります。

メールアドレスを持たないため、

> 「パスワードを忘れました → メール送信」

が使えません。

したがってアカウント作成時に、

**Recovery Code**

を発行します。

例：

```text
Market ID
MKT-7F4K-29QX
Recovery Code
8GHD-X19P-K7QT
```

Recovery Codeによって新しいパスワードを設定できます。

さらに教員管理画面から、

> Market IDを指定 → パスワード初期化

もできるようにします。

教員も、

「これは田中君のアカウント」

という情報をシステムに登録する必要はありません。

## 37. 教員が誰なのか把握する方法

授業なので最終的には、

> この成績は誰のものか

が必要になる可能性があります。

しかし、それを**システム側で持つ必要はありません。**

例えば教員だけが別途、

| 生徒  | Market ID     |
| ----- | ------------- |
| 生徒A | MKT-7F4K-29QX |
| 生徒B | MKT-93HF-X2LQ |

という対応表を学校側で管理する。

本システムには入れない。

これなら仮にシステムのDBが漏れても、

```text
MKT-7F4K-29QX
NEKO DESIGN
87,500MP
売上23,000MP
```

までしか分かりません。

本人特定情報がありません。

これは今回の用途にはかなり相性がいいです。

## 38. 表示名

市場に表示するのは原則、

**企業名**

です。

生徒名ではありません。

例えば、

```text

SNS用ロゴ制作
2,500MP
★★★★☆ 4.2
広告制作・デザイン
```

という普通のECサイトとして見せます。

これも重要です。

「○○君の商品だから買う」

を弱められるため、以前問題になった**仲良し購入対策にもなる**からです。

可能なら授業序盤は、

> 誰がどの企業を運営しているか公開しない

方式でも面白いです。

教材っぽくしません。

## 43. 「販売できる品質」の定義

ここも要件として入れた方がいいです。

# 第2部 MVP 受け入れ基準

**MVP は下の A〜K が全て満たされた時点で「リリース可」とする。1つでも欠ければ不可。**

数値には2種類ある。**既定値**と書いたものは管理者が画面から変更できるようにする。それ以外は
固定値として実装する。

## A. 匿名アカウント（要件 35・36・37）

| 番号 | 基準                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1   | アカウント作成時に Market ID（`MKT-XXXX-XXXX` 形式、英大文字と数字、紛らわしい `0 O 1 I` を除く）と Recovery Code（`XXXX-XXXX-XXXX`）が**一度だけ**表示される。以後どこにも再表示されない。Recovery Code は DB にハッシュのみ保存                                                                                                                                                                                                                                                             |
| A2   | Market ID とパスワードでログインできる。ID が存在しない場合とパスワードが違う場合で**同じエラー文言**が出る（ID の存在を漏らさない）                                                                                                                                                                                                                                                                                                                                                          |
| A3   | **生徒の個人情報がデータベースに1件も入っていない。** 検査スクリプトが CI で毎回走り、違反0件で通る。検査は2段構え: (a) **この仕組みが自分で作ったテーブル**には、氏名・メールアドレス・電話番号・住所・生年月日・学籍番号・外部サービスのアカウント ID を入れる**列が存在しない**。(b) **Mercur / Medusa から引き継いだテーブル**にはそれらの列が残るが、**中身が空か、`MKT-XXXX-XXXX@anon.invalid` のような機械生成の値だけ**である。生徒がそれらの項目を入力できる画面・API を一切持たない |
| A4   | Recovery Code を入力すると新しいパスワードを設定できる。使用済み Recovery Code は二度と使えず、新しい Recovery Code が1回だけ表示される                                                                                                                                                                                                                                                                                                                                                       |
| A5   | 管理者画面で Market ID を指定すると一時パスワードが発行され、画面に表示される                                                                                                                                                                                                                                                                                                                                                                                                                 |
| A6   | パスワードは8文字以上。DB にはハッシュのみ保存。ログイン失敗が連続5回（既定値）で15分（既定値）ロックされる                                                                                                                                                                                                                                                                                                                                                                                   |

## B. 企業と初期資金（要件 2・3）

| 番号 | 基準                                                                                               |
| ---- | -------------------------------------------------------------------------------------------------- |
| B1   | アカウント作成と同時に仮想企業が1社できる。企業名は1〜40文字、他社と重複できず、後から変更できる   |
| B2   | 企業作成時に通常残高 100,000 MP（既定値）が入り、取引履歴に「初期資金 +100,000」が1行残る          |
| B3   | 全企業について「現在残高 = 取引履歴の合計」。整合性チェックコマンドを実行すると差分0件と表示される |

## C. 商品（要件 5・6・7）

| 番号 | 基準                                                                                                                                                 |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1   | 商品名・商品説明・ターゲット顧客・解決する課題・販売価格・提供可能数・商品画像・販売期間のいずれかが欠けていると登録できず、欠けた項目にエラーが出る |
| C2   | 登録した商品が市場一覧に出る。販売期間外の商品と提供可能数0の商品は「購入できない」と表示される                                                      |
| C3   | 販売価格は1MP以上の整数。0や負数、小数は登録できない                                                                                                 |

## D. 購入と MP 移転（要件 8・9）

| 番号 | 基準                                                                                                                     |
| ---- | ------------------------------------------------------------------------------------------------------------------------ |
| D1   | 購入すると「購入者 −価格」「販売者 +価格」が**1つのトランザクション**で反映される。片方だけ動いた状態は存在しない        |
| D2   | 自社商品は購入ボタンが押せない。API を直接呼んでも 4xx で拒否される                                                      |
| D3   | 残高（ボーナス+通常）が価格に満たない場合は購入できない。API を直接呼んでも拒否される                                    |
| D4   | 購入すると提供可能数が1減る。0になった商品は購入できない                                                                 |
| D5   | 取引履歴に購入者側・販売者側の両方の行が残り、双方の画面から見える。相手の表示は**企業名のみ**（Market ID を表示しない） |

## E. ボーナス MP とテスト（要件 32・33・42）

| 番号 | 基準                                                                                                                                         |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| E1   | 支払いはボーナス残高から先に、足りない分を通常残高から引く。通常10,000／ボーナス1,500の企業が2,000の商品を買うと、ボーナス0／通常9,500になる |
| E2   | ボーナスには有効期限がある。期限を過ぎたボーナスは残高表示にも支払いにも使われず、取引履歴に「失効」の行が残る                               |
| E3   | 同じテストからボーナスを受け取れるのは1回だけ。2回目以降の受験では付与されない                                                               |
| E4   | 採点はサーバー側で行う。問題を取得する API の応答に正解が含まれない（ブラウザの通信内容を見て確認できる）                                    |
| E5   | 得点からボーナス額への換算表（既定値: 60未満=0／60〜79=500／80〜89=1,000／90〜100=1,500 MP）を管理者が画面から変更できる                     |
| E6   | 商品を売って受け取った MP は通常残高に入る。ボーナス残高は他社へ移転しない                                                                   |

## F. 広告（要件 12・13）

| 番号 | 基準                                                                                             |
| ---- | ------------------------------------------------------------------------------------------------ |
| F1   | 企業は MP を支払ってトップページの「Featured」枠を期間指定で購入できる。支払い順序は E1 と同じ   |
| F2   | 表示回数・クリック数・CTR・広告経由の購入数・広告費・売上・ROAS が企業ダッシュボードに表示される |

## G. ダッシュボードとランキング（要件 16・25）

| 番号 | 基準                                                                                                                         |
| ---- | ---------------------------------------------------------------------------------------------------------------------------- |
| G1   | 残高（通常・ボーナス別）・売上・支出・利益・販売数・購入数・広告費・商品別売上が表示され、取引履歴から再計算した値と一致する |
| G2   | ランキングを 売上／利益／利益率／顧客数／ROAS の5指標で切り替えられる。表示は企業名のみ                                      |

## H. 管理者（要件 20・21・22・26）

| 番号 | 基準                                                                                                            |
| ---- | --------------------------------------------------------------------------------------------------------------- |
| H1   | 全企業の残高・売上・利益・取引・商品・広告を一覧できる                                                          |
| H2   | 企業ペアごとの相互取引率（A→B と B→A の合計額 ÷ 両社の総取引額）が表示され、30%（既定値）を超えた組が強調される |
| H3   | 企業ごとの購入集中率（購入先上位1社が占める割合）が表示される                                                   |
| H4   | 管理者の購入ログ（管理者別の購入先・金額・回数）を管理者同士で閲覧できる                                        |

## I. 多言語（要件 34）

対応言語は `ja-JP` / `en` / `zh-CN` / `vi-VN` / `ne-NP` / `th-TH` の6つ。

| 番号 | 基準                                                                                                                                                                                                                           |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| I1   | 言語切替が全画面の右上に常設され、ログインしていなくても切り替えられる。選んだ言語はブラウザに保存され、次に開いたときも保たれる                                                                                               |
| I2   | 要件34の翻訳対象（ナビ・ボタン・エラー・商品登録・購入・ダッシュボード・MP残高・広告・テスト・ランキング・管理画面・ルール説明・チュートリアル）の UI 文字列について、6ロケールのキー集合が一致し、未翻訳キーが0件（機械検査） |
| I3   | 商品名・商品説明は「原文 + 任意の各言語翻訳」。閲覧者の言語の翻訳があればそれを、無ければ原文を表示する                                                                                                                        |
| I4   | **合格条件**: 日本語を読めない状態を想定し、日本語以外の1言語だけで「アカウント作成 → 商品登録 → 他社商品購入 → ダッシュボード閲覧」を、説明なしで最後まで到達できる（人が実際に操作して確認）                                 |

## J. デザイン（要件 38・39・40・41・42・43）

| 番号 | 基準                                                                                                                                                                                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| J1   | 白背景・薄いグレー・黒に近い文字・アクセントカラー1色。要件40の禁止モチーフ（黒板・鉛筆・ノート・学校アイコン・子供向けイラスト・ゲーム風UI・RPG風ゲージ・コイン演出・PowerPoint教材風）が全画面に無いことを、チェックリストで人が確認 |

| 番号 | 基準                                                                                                             |

## MVP に含めないもの

要件30の第2段階（クーポン・市場調査の有料化・顧客セグメント・教員購入ミッション・法律イベント・
融資・倒産・株式・仕入れ・BtoB・市場ニュース）と、要件14の販促のうち値引き以外、要件15の有料
市場調査、要件20の循環取引の自動検知は MVP に含めない。MVP 稼働後に `docs/plan.json` へ追記する。

先に決まらないと数値を置けない。市場が動き始めてから決めた方が確実。
